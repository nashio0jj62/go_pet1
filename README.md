# Payway

Платёжный шлюз на Go, Kafka и PostgreSQL с тестовым HTTP-провайдером.
Создание, обработка, отмена платежей и история событий. Реальных списаний нет.

## Запуск

Нужны Docker и Docker Compose.

Создайте в корне `.env` с разными случайными значениями из цифр и букв `a-f`:

```dotenv
POSTGRES_PASSWORD=<пароль БД>
CALLBACK_SECRET=<секрет длиной не менее 32 символов>
GRAFANA_ADMIN_PASSWORD=<пароль Grafana>
```

Запустите из корня проекта:

```bash
docker compose up --build
```

API: `http://localhost:8080`. Миграция существующей БД применяется сервисом `migrate`.
Если уже запускали предыдущую версию, добавьте недостающие переменные в свой `.env`.

## Обработка команд и событий

- `api` принимает HTTP-запросы и вебхуки PSP. Он публикует команды в `payment.commands` и читает текущее состояние из PostgreSQL.
- `worker` читает команды в группе `payment-workers`, вызывает PSP и публикует события в `payment.events`.
- `projection` читает события в группе `projections`. Он сохраняет историю в `payment_events` и обновляет `payments` в одной транзакции. Событие с пропуском версии хранится до появления предыдущих версий.

`worker` и `projection` запускаются отдельными контейнерами. Worker ждёт,
пока опубликованное им событие применится к проекции. При временной недоступности
проекции он повторит незавершённую команду. Группы Kafka сохраняют свои имена и позиции при обновлении.

Идемпотентность проверяется на трёх уровнях:

1. API резервирует идентификатор и отпечаток запроса в `payment_requests`. Повтор с теми же данными сохраняет прежний ID, а изменённые данные дают `409`.
2. Worker сверяет ID команды и отпечаток её данных в `processed_commands`. Он отмечает команду выполненной после успешной обработки. Если запись ещё не сделана, обработка может продолжиться с сохранённого состояния, а повторный вызов PSP использует прежний `payment_id` как ключ идемпотентности. При обновлении старые записи без отпечатка не считаются подтверждением выполнения команды целиком.
3. Проекция сверяет ID и данные события в `payment_events`. Повтор того же события не добавляет новую версию и не увеличивает счётчики платежей.

## Платежи

```bash
curl -i -X POST http://localhost:8080/payments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-001' \
  -d '{"merchant_id":"demo-shop","amount":12500,"currency":"KZT"}'
```

Сумма в минимальных единицах валюты: `12500` = `125.00 KZT`.
Для нового платежа нужен новый `Idempotency-Key`, для повтора — прежний ключ и те же данные.

Подставьте `payment_id` из ответа:

```bash
curl 'http://localhost:8080/payments/<payment_id>'
curl 'http://localhost:8080/payments/<payment_id>/events'
curl -X POST 'http://localhost:8080/payments/<payment_id>/cancel'
```

Обработка асинхронная: после создания возможен короткий `404`, затем `NEW` и `PROCESSING`.
Тестовый провайдер завершает платёж примерно через 8 секунд:

- `12500` — успешный платёж (`COMPLETED`).
- `12513` — отказ (`FAILED`): любые суммы, заканчивающиеся на `13`.
- `12599` — остаётся в `PROCESSING` для проверки отмены: суммы, заканчивающиеся на `99`.

Отмена возвращает `202`, результат нужно читать через GET. Уже завершённый платёж
не отменяется. При гонке с завершением итог определяет провайдер.
Старые платежи в `NEW` можно запустить повтором исходного POST с прежним ключом.
История поддерживает `?after_version=2&limit=50` (максимум 100 событий).

Callbacks отправляются провайдером автоматически на `POST /callbacks/mock`.
Подпись — HMAC-SHA256 от `timestamp + "." + body` с ключом `CALLBACK_SECRET`;
заголовки `X-Callback-Timestamp` и `X-Callback-Signature`, допуск времени — 5 минут.
Один `event_id` нельзя повторять с другим содержимым.

Примеры запросов: [examples/payments.http](examples/payments.http).

Пока нет авторизации пользователей, реальных PSP, DLQ и автоматического
восстановления потерянных публикаций. Непригодное для обработки
сообщение задерживает consumer до устранения причины. Это локальная версия для разработки.

## Мониторинг

- Grafana: `http://localhost:3000`, логин `admin`, пароль из `GRAFANA_ADMIN_PASSWORD`.
  Дашборд **Payway** подключается автоматически.
- Jaeger: `http://localhost:16686`. Найдите trace по заголовку ответа `X-Trace-ID`
  или по тегу `payment.id` и сервису `payway-api`.
- Prometheus: `http://localhost:9090`.

Метрики передаются через OpenTelemetry Collector каждые 5 секунд, Prometheus
забирает их раз в 10 секунд. После первого запроса данные появляются не сразу.
Worker и projection отправляют телеметрию через OTLP и не открывают HTTP-порты.

Счётчики платежей учитывают новые события после commit проекции и сбрасываются
при перезапуске projection. Время платежа считается от создания до конечного статуса.
Prometheus хранит метрики 7 дней в Docker-томе; Jaeger хранит трассы в памяти
и теряет их при перезапуске. Старые платежи получают trace при следующем запросе;
уже выполненные до этого этапы в нём не появятся.

В Compose задан `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317`.
Для запуска приложений отдельно можно задать другой OTLP gRPC endpoint
или отключить экспорт через `OTEL_SDK_DISABLED=true`.
